# MITRE ATT&CK for ICS coverage

Generated by `ot-ids/tools/attack_ics.py coverage` from ATT&CK for ICS 19.2. Do not edit by hand:
change the tables in `ot-ids/attack/` and run the tool again.

Scope: the detections kept in this repository (the shared rules in `platform/detections`, the OT IDS rules in `ot-ids/detections`), the YARA rules, the Zeek ACID package the product loads, and the layer 2 watch. Imported rule sets are not counted here; a build writes this same report for everything it ships to `out/attack-ics-coverage.md`. The general rule set bundled with the product (Emerging Threats Open) is not counted in either: its rules carry ATT&CK Enterprise techniques, not ICS ones.

## How to read this

- **Direct**: a detection matches the network operation the technique is carried out with.
- **Related only**: a detection matches something that goes with the technique, or a wider operation of which
  the technique is only one use. In the tables, related detections are in brackets.
- **None**: nothing here is mapped to the technique.

A detection mapped to a technique means the sensor has a rule for one way of doing it, on the protocols that
rule covers. It does not mean every way of doing it is seen, and no alert says by itself that an operation was
unauthorised. MITRE's own caution applies: covering a technique does not guarantee full defensive coverage.

## Gaps

Sorted by where MITRE's detection guidance says each technique shows up (its data components).

### In network traffic, with no detection here (21, sub-techniques included)

MITRE lists network traffic among the data these can be detected with. That is not the same as a rule being
possible: the note on each says what it would take.

- **T0800 Activate Firmware Update Mode.** The command that puts a device into firmware update mode is different for each vendor; a rule needs a capture of each one.
- **T0802 Automated Collection.** Shows as steady reading from an address that does not normally read. The three OT anomaly detectors (shipped switched off) are the nearest thing; there is no rule.
- **T0817 Drive-by Compromise.** Web browsing from the control network. The general rule set bundled with the product is where exploit-kit rules live; it is not counted on this page.
- **T0819 Exploit Public-Facing Application.** Exploits of known vulnerabilities are in the general rule set bundled with the product, listed by CVE in the build's vulnerability coverage report; they are not counted on this page.
- **T0848 Rogue Master.** Needs the list of real masters. Set MODBUS_CLIENT and DNP3_CLIENT on the sensor and the imported Quickdraw rules name commands from any other address.
- **T0860 Wireless Compromise.** Radio links are not on the wire the sensor listens to.
- **T0864 Transient Cyber Asset.** A new laptop on the network appears in the product's asset inventory; no alert is defined for it here.
- **T0865 Spearphishing Attachment.** Email is not normally carried on a control network; this belongs to the mail gateway.
- **T0884 Connection Proxy.** Proxy and tunnelling tools have nothing specific to industrial networks to match on; the general rule set is where such rules belong.
- **T0885 Commonly Used Port.** The imported Quickdraw set has rules for another protocol on the Modbus and DNP3 ports. Nothing in this repository does it.
- **T0886 Remote Services.** RDP, SSH and file sharing inside the network are normal engineering traffic; they become a signal only against a record of who normally uses them. The correlation rules use remote access from outside as their first step.
- **T0887 Wireless Sniffing.** Radio links are not on the wire the sensor listens to.
- **T0892 Change Credential.** Password-change commands are different for each vendor; a rule needs a capture of each one.
- **T1691.001 Block Operational Technology Message: Command Message.** A blocked command shows as traffic that stops. That needs a baseline of what is expected, which rules do not have.
- **T1692.002 Unauthorized Message: Reporting Message.** A false report cannot be told from a true one without knowing the real process value. Reports from an address that is not the device could be caught with a list of devices.
- **T1693.002 Modify Firmware: Module Firmware.** On most protocols a module's firmware arrives the same way as the device's own; the rules here cannot tell them apart.
- **T1694 Insecure Credentials.** Default and hardcoded passwords can be matched where logins are not encrypted (Telnet, FTP, plain HTTP), one product at a time. The imported ELITEWOLF set does it for SEL relays.
- **T1694.001 Insecure Credentials: Default Credentials.** Default passwords can be matched where logins are not encrypted, one product at a time. The imported ELITEWOLF set does it for SEL relays.
- **T1694.002 Insecure Credentials: Hardcoded Credentials.** Hardcoded passwords can be matched where logins are not encrypted, one product at a time. Nothing here does.
- **T1695.001 Block Communications: Serial COM.** The serial link itself is not on the Ethernet the sensor listens to. MITRE's example is a TCP session held open to the serial-to-Ethernet converter so nothing else can use it; catching that needs the list of converters and the addresses allowed to connect to them.
- **T1695.003 Block Communications: Wi-Fi.** Radio links are not on the wire the sensor listens to.

## Where the technique appears in the product

- Suricata alerts carry it in the alert itself: the build writes `mitre_tactic_id`, `mitre_tactic_name`,
  `mitre_technique_id` and `mitre_technique_name` into each mapped rule, and the product turns those into the
  `threat.tactic.*` and `threat.technique.*` fields and adds the tactic to the alert's category.
  A sub-technique is kept in the alert's `mitre_subtechnique_id`, and `td_attack_fit` says whether the rule's
  first technique is a direct or a related one. An alert carries its rule's first technique and every direct one.
- Zeek ACID notices carry it already (category ATTACKICS).
- The layer 2 watch and YARA matches do not carry it; this page is where they are mapped.
